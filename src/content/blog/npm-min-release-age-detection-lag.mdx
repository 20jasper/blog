To make the title punchy, some liberties were taken. To be more precise, the last 5 years of OSV records show a `minimumReleaseAge` of 1 day would block 53% of single version, _reported_ npm supply chain attacks, or around 10,000 attacks. A short delay keeps supply chain attacks at bay!

{/* 1. Developers rely on a huge amount of software, therefore */}

## The dependencypocolypse

It's become increasingly easy to unconsciously install obscene amounts of software. Dependencies used to require selfhosting a package and its dependencies. Nowadays, an npm account will do

The barrier to depending on a package is gone—many packages rely on chains of many more packages. For example, [globby](https://main.npmx.dev/package/globby) is a small scoped package with 23 dependencies

![large stack of rectangular stones representing npm packages holding up the globby package](/globby-dependency-stack.svg)

{/* 2. One malicious package version can affect a huge amount of users (transitive deps), but */}
There are many issues with large amounts of dependencies—most pertinently, supply chain risk. One compromised package in the chain can leak your AWS token or drain your airplane miles. Globby has 92,820,552 downloads per week as of writing, so even a small vulnerability window would affect many users.

[stylelint](https://npmx.dev/package/stylelint) depends on globby and has 110 total dependencies. [A default Next.js app](https://npmx.dev/package/create-next-app)[^nextTemplate] has 8 direct dependencies and 359 total dependencies!

[^nextTemplate]: Installed via `npx --yes create-next-app@latest my-app --typescript --eslint --tailwind --app --src-dir --import-alias "@/*" --use-npm --no-turbopack` and measured with `npm ls --all --parseable | tail -n +2 | wc -l`

{/* 2a. the increase in advisories is concerning, but */}
To add fuel to the fire, security advisories have steadily increased. This doesn't necessarily mean supply chain attacks are increasing, but it's definitely correlated. Importantly, advisories come after an attack—after many have already installed the package!

<MonthlyDetectionsChartTanstack />

Structured reports like OSV's have made tracking easier. Prior to the last 5 years, disclosure would be a blog post or GitHub issue. Additionally, there is better automated security scanning than 5–10 years ago, and the prevalence of LLMs has renewed interest in security

To make matters even worse, attacks have become much more sophisticated. Since September 2025, there have been 4 worms affecting at least 2600 packages[^worm]. A worm steals maintainer's credentials to publish more malicious packages to attack further maintainers

For many, going dependencyless isn't realistic. A Next.js developer shan't have to read 305 MB of code before writing a page. Security researchers, automated scanners, and maintainers all catch supply chain attacks, but this takes time, and advisories lag hours to days

{/* 4. Waiting is a simple way to protect you since it gives scanners, researchers and maintainers time to act, but */}

## Just wait

A simple solution to avoid many supply chain attacks is to just wait for security scanning. PNPM calls this `minimumReleaseAge`, but every major JavaScript package manager has a similar setting to delay package installation until it's old enough

Many attacks are resolved very quickly. Of detected, single version npm supply chain attacks, 16.3% are removed from npm within 1 hour of publishing

<ThresholdCurveChartTanstack chart={PUBLISH_TO_YANK_CHART} />

This is a lower bound—not every supply chain attack is discovered or reported

{/* 5. there is tension between sitting on an old version and protection, therefore */}
Waiting months will reduce vulnerability, but you'll miss out on new features and ironically need to bump further for security patching!

3 days seems to be the sweet spot for most projects that want new packages. 68.7% of detected npm packages are removed by that time. Waiting another 27 days brings diminishing returns, with 74.8% of packages removed

## Closing thoughts

I wrote this article since I could not find any large scale analysis of minimum release ages. There are a few great articles, such as [We should all be using dependency cooldowns](https://blog.yossarian.net/2025/11/21/We-should-all-be-using-dependency-cooldowns), though each of them lists at most 10 case studies

I often see arguments like "won't the vulnerabilities just go unnoticed for the default delay?", and now I have the proof that many times, a security scanner will catch the issue quickly
